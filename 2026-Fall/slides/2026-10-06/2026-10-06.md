# Accessibility

## Building for everyone


## Who are we building for?

- **Vision** — blind, low vision, color blind
- **Hearing** — deaf or hard of hearing
- **Motor** — can't use a mouse, uses keyboard only, tremors
- **Cognitive** — dyslexia, ADHD, memory, processing speed

Roughly **1 in 4 adults** in the US has some disability.

---

## It's not just permanent disability

| Permanent | Temporary | Situational |
|---|---|---|
| Blind | Eye surgery | Sun glare on your phone |
| One arm | Broken arm | Holding a baby |
| Deaf | Ear infection | Loud restaurant |


---

## Two more reasons

**Legal**:  the ADA applies to websites. Public universities, government agencies, and businesses get sued over inaccessible sites regularly.

**Practical**:  search engines are, functionally, blind users. Almost everything that helps a screen reader helps your SEO.

---

## POUR

The four principles behind every accessibility guideline:

- **P**erceivable — users can sense it
- **O**perable — users can use it
- **U**nderstandable — users can make sense of it
- **R**obust — it works with their tools

---

## Perceivable

Can the user take the information in at all?

- Images have alt text
- Videos have captions
- Color isn't the *only* way you convey something
- Enough contrast between text and background

---

## Operable

Can the user actually work the thing?

- Everything reachable by keyboard alone
- Nothing that flashes rapidly
- Enough time to complete tasks
- Users can skip repetitive navigation

---

## Understandable

Does it make sense?

- Plain language
- Predictable navigation — same place on every page
- Form errors that say what's wrong and how to fix it
- `<html lang="en">` so screen readers use the right pronunciation

---

## Robust

Does it work with assistive technology?

- Valid HTML (this is why we run the validator)
- Semantic tags
- Works across browsers and screen readers

---

## WCAG

**Web Content Accessibility Guidelines** — published by the W3C. The standard everyone measures against.

Three levels:

- **A** — bare minimum
- **AA** — the practical target, and what most laws require
- **AAA** — very strict, rarely required across a whole site

**Aim for AA.**

---

## Good news: you've been doing this since week two

Remember the semantic HTML list?

```html
<header>
  <nav>...</nav>
</header>
<main>
  <h1>Page title</h1>
  <article>...</article>
</main>
<footer>...</footer>
```

Semantic HTML gets you most of the way to accessible. A screen reader can jump straight to `main`, list all the headings, or skip the nav.

---

## Alt text

```html
<!-- Bad -->
<img src="dog.jpg" alt="image" />
<img src="dog.jpg" alt="dog.jpg" />

<!-- Good -->
<img src="dog.jpg" alt="A golden retriever catching a frisbee" />
```

---

## Alt text rules

- Describe the **content and purpose**, not the file
- Don't start with "image of" — the screen reader already said that
- If the image is **decorative**, use empty alt: `alt=""`
  - Empty alt means "skip this." A *missing* alt means the screen reader reads the filename out loud.
- If the image is a link, describe where it goes

---

## Headings are navigation

Screen reader users pull up a list of headings to navigate — like a table of contents.

- One `<h1>` per page
- Don't skip levels (`h2` → `h4`)
- **Never** pick a heading level because of how big it looks. That's what CSS is for.

---

## Color contrast

Text needs enough contrast against its background.

- **4.5:1** for normal text (AA)
- **3:1** for large text (24px+, or 19px+ bold)

Light gray text on white looks elegant and is unreadable for a lot of people.

Check it: WebAIM Contrast Checker, or the contrast readout in DevTools.

---

## Color alone is never enough

```html
<!-- Bad: color blind users see nothing -->
<p style="color: red;">This field is required</p>

<!-- Good: color AND text AND an icon -->
<p class="error">⚠ Error: Email address is required</p>
```

About **1 in 12 men** is color blind. Always pair color with text or shape.

---

## Keyboard navigation

Some users never touch a mouse.

- `Tab` moves forward, `Shift + Tab` moves back
- `Enter` activates links and buttons
- `Space` toggles checkboxes and scrolls

**Try it now:** tab through your own site. Can you reach everything? Can you tell where you are?

---

## Never do this

```css
/* Removes the focus outline - now keyboard users are lost */
*:focus {
  outline: none;
}
```

If the default outline is ugly, **replace** it — don't delete it:

```css
*:focus-visible {
  outline: 3px solid #0066cc;
  outline-offset: 2px;
}
```

---

## Use the right element

```html
<!-- Bad: not focusable, not keyboard-activatable -->
<div onclick="submit()">Submit</div>

<!-- Good: works with keyboard and screen readers -->
<button onclick="submit()">Submit</button>
```

A `<div>` is not a button. A `<span>` is not a link. Use the real element and you get accessibility built in.

---

## Forms (recap from week 3)

```html
<label for="email">Email address</label>
<input type="email" id="email" name="email" required />
```

The `for` / `id` pair is what lets a screen reader announce "Email address, edit text, required."

Placeholder text is **not** a label — it disappears when you start typing.

---

## ARIA

**Accessible Rich Internet Applications** — extra attributes that describe things HTML can't.

```html
<button aria-label="Close menu">✕</button>
```

Without `aria-label`, a screen reader announces this button as just "✕".

---

## The first rule of ARIA

> **Don't use ARIA.**

Use the correct HTML element instead. Native HTML is accessible by default; ARIA only *describes* — it doesn't add behavior.

```html
<!-- Don't -->
<div role="button" tabindex="0">Save</div>

<!-- Do -->
<button>Save</button>
```

Bad ARIA is worse than no ARIA.

---

## The three ARIA attributes worth knowing

```html
<!-- Label something with no visible text -->
<button aria-label="Search">🔍</button>

<!-- Point at existing text as the label -->
<nav aria-labelledby="main-nav-heading">

<!-- Hide decorative junk from screen readers -->
<span aria-hidden="true">→</span>
```

## Tools

- **WAVE** — browser extension, visual overlay of problems. Easiest to start with.
- **axe DevTools** — browser extension, developer-focused, very few false positives
- **Lighthouse** — built into Chrome DevTools, gives you a score
- **WebAIM Contrast Checker** — for color pairs

---

## An honest warning about tools

Automated tools catch roughly **30-40%** of accessibility problems.

They can tell you an alt attribute is missing. They cannot tell you that `alt="dog"` should have been `alt="A golden retriever catching a frisbee"`.

**Tools find problems. People find the rest.**

## In-class exercise

Run your own project through WAVE or axe:
